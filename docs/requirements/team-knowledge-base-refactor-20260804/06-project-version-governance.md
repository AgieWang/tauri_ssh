# 06 项目版本治理确认

- 状态：Proposed
- 对应用户需求：6

## 1. 版本定义

项目版本不是一个简单字符串，而是一份多仓库不可变清单：

| 字段 | 含义 |
|---|---|
| 项目版本名称 | 面向用户的业务版本，如 `v2.3.0` |
| 仓库绑定 | 清单中的具体微服务仓库 |
| 请求引用 | 用户选择的 Tag、分支或 Commit |
| 解析 Commit | 创建时确定并固化的完整 SHA |
| 采集类型 | tag / branch / commit / worktree |
| 状态 | 已映射、排除、失败、等待采集 |
| 采集时间 | 形成证据切片的时间 |

## 2. Branch、Tag 与 Commit 语义

- Tag/Commit：创建后视为固定证据。
- Branch：是会移动的选择规则；每次创建或刷新都生成新的清单记录，旧版本不改变。
- Worktree：可含未提交内容，只能作为明确标记的临时快照，默认不用于发布版本。

## 3. 多仓库映射

系统优先推荐所有仓库共同存在的 Tag。若某仓库缺少该 Tag，用户可为该仓库选择其他 Tag/分支/Commit，或明确排除；不得静默使用 HEAD。

版本只有在所有启用仓库都已映射或明确排除后，才能进入“清单完成”；解析、索引、向量、图谱和分析全部完成后才是“可完整使用”。

## 4. 版本隔离

同步、文档绑定、代码分析、搜索、图谱、向量和问答必须携带项目版本/仓库快照范围。任何无范围的旧 API 只能在兼容层补安全默认，不能自动选择“最新版本”作为历史事实。

## 5. 当前状态

- 仓库绑定和版本清单表、Command/API 已存在。
- 通过 Tag/分支/Commit 形成清单的基础任务已完成。
- 文档统一绑定、完整度计算、新版本页面和跨版本隔离验收仍待完成。

## 6. 验收用例

- 4 个仓库共享同名 Tag，一次确认形成清单。
- 两个仓库使用不同发布标签，仍能形成同一项目版本。
- 某仓库缺 Tag 时阻止就绪，直到覆盖或排除。
- 分支向前移动后旧版本仍引用旧 Commit。
- 历史版本问答不会引用后续实现。

## 7. 请确认

- **C06-1（推荐）**：项目版本使用多仓库不可变 Commit 清单。
- **C06-2（推荐）**：分支每次采集固化 Commit，刷新产生新记录。
- **C06-3（推荐）**：缺失仓库必须覆盖或排除，禁止回退到 HEAD。
- **C06-4（推荐）**：只有完整度达到门禁才显示“可完整使用”。
- **C06-5（待选择）**：是否允许把 worktree 快照绑定正式项目版本？推荐不允许，只用于临时分析。
