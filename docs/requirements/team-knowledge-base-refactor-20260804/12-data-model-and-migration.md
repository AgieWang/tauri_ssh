# 12 数据模型与 SQLite 迁移确认

- 状态：Proposed
- 对应用户需求：全部数据持久化能力

## 1. 当前基线

当前源码 `src-tauri/src/database/schema.rs` 的 `SCHEMA_VERSION` 为 **39**。旧设计中的 v36 是 2026-08-03 的历史基线，实施时必须以 v39 或后续最新值继续追加，不复用或重排迁移号。

本次只核对了源码迁移和 DAO；没有把某个本机运行数据库声明为已完成升级或真实数据验收。

## 2. 核心表族

| 表族 | 主要实体 |
|---|---|
| 目录 | projects、releases、repository_bindings、release_manifests |
| 文档 | documents、versions、drafts、version_bindings、uploads |
| 资产/解析 | assets、parse_artifacts、chunks |
| 搜索/向量 | title_index、FTS、embedding_profiles、chunk_embeddings |
| 分析 | code_snapshots/files/elements/relations、analysis_runs/drafts |
| 图谱 | graph_builds/nodes/edges、来源关系表 |
| 任务/评测 | jobs、backfill_runs、coverage、evaluation_runs、feature_flags |

## 3. 关键不变量

- 逻辑文档有稳定 ID；提交版本不可变。
- 资产按内容哈希去重，引用计数与实际绑定一致。
- 文档版本必须显式绑定项目版本或跨版本范围。
- 项目版本清单中的 resolved Commit 创建后不可变。
- 草稿、删除、权限不可见和解析失败正文不进入活动索引。
- 图谱、标题、FTS 和向量均为可重建派生数据。
- 外键/唯一约束、软删除和时间格式以当前迁移契约为准。

## 4. 迁移策略

1. 启动迁移只做短小、必须原子完成的 DDL/DML。
2. 标题回填、Office 重解析、向量和图谱构建进入后台任务。
3. 新表与兼容 Facade 先上线，再逐域切换读取和写入。
4. 派生回填失败不删除原数据，也不阻塞旧基础入口。
5. 新数据库版本拒绝被旧应用打开，避免未知结构写坏。

## 5. 回滚策略

SQLite `user_version` 不向下降级。回滚通过功能开关恢复旧 Facade/旧活动索引；原始资产、文档版本和版本清单继续保留。出现迁移故障时先复制数据库做离线诊断，不在原库上反复试验破坏性修复。

## 6. 迁移验证矩阵

- 空库初始化到最新版本。
- v36、v37、v38、v39（若目标版本更高）逐级升级。
- 含项目、版本、文档、向量、关系和任务数据的代表性副本升级。
- 中途失败、再次启动、未来版本拒绝、唯一约束冲突。
- 迁移前后各表数量、当前版本指针、引用计数和孤立记录核对。
- 大型回填的暂停、继续、取消、失败隔离和幂等。

## 7. 请确认

- **C12-1（推荐）**：以当前 v39 为最低事实基线，实施前再次读取最新版本。
- **C12-2（推荐）**：只追加前向迁移，不删除/重排历史迁移。
- **C12-3（推荐）**：大型派生回填不在应用启动事务中执行。
- **C12-4（推荐）**：数据库回滚采用功能/索引切换，不降级 `user_version`。
- **C12-5（待选择）**：迁移前是否自动创建本地备份？推荐对跨版本升级创建一次受控备份，并设置保留策略和空间预检。
