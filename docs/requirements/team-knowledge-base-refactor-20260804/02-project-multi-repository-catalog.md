# 02 项目与多 Git 仓库目录确认

- 状态：Proposed
- 对应用户需求：1、6

## 1. 推荐业务模型

一个知识项目可关联多个已在“Git 工作区”登记的仓库。每个绑定保存：业务别名、仓库角色、默认分支、版本策略、启用状态、最近检查/同步状态和审计时间。

项目创建只要求名称和可选描述；内部项目键由系统生成。仓库角色、逐仓库规则和排除策略放入高级设置。

## 2. 主要规则

- 项目名称规范化后唯一；重复时返回可定位到名称字段的冲突。
- 同一项目和同一 Git 工作区只能有一个有效绑定。
- 批量关联采用事务：任一绑定失败时不保留部分成功。
- 仓库检查只读，可读取状态、HEAD、分支、Tag 和对象；禁止 checkout、stash、reset、clean、pull、push、Hook 和脚本。
- 脏工作树可以被识别，但不能被称为发布版本；历史版本应读取 Commit 对象。
- 解除关联为停用，不删除历史版本清单、文档、引用和审计。

## 3. 当前可复用实现

- 新目录页和四步项目设置页已存在。
- `knowledge_project_repository_bindings` 和 `knowledge_release_repository_manifests` 已进入 schema v37+ 链路。
- 分域 Catalog Command/API 已覆盖列表、批量替换、解除、可用性检查和版本清单。
- 仍需用真实多仓库、重复绑定、脏仓库和解除关联场景做运行时闭环。

## 4. 实施任务

1. 固化项目 CRUD 和稳定错误码。
2. 仓库选项只来源于 Git 工作区，不让用户直接输入任意路径。
3. 批量保存前预检查重复、移除工作区和不可读仓库。
4. 为每个仓库生成只读可用性摘要和处理建议。
5. 关联完成后进入项目版本创建，不要求用户理解 Git 命令。

## 5. 验收用例

- 新建项目并一次关联 4 个微服务仓库。
- 一个仓库重复、一个已移除时整批失败且无残留绑定。
- 仓库有未提交改动时显示“存在本地改动”，但不修改仓库。
- 解除关联后历史版本和引用仍能查看，新同步停止。
- 不存在 Git 工作区时显示如何先登记工作区的可操作空态。

## 6. 请确认

- **C02-1（推荐）**：仓库只能从已有 Git 工作区选择，不开放任意路径输入。
- **C02-2（推荐）**：批量关联采用全成全败事务。
- **C02-3（推荐）**：解除关联保留全部历史证据，仅停止后续同步。
- **C02-4（推荐）**：脏工作树只允许显式采集为 `worktree` 快照，不视作正式 Tag/分支版本。
- **C02-5（待选择）**：一个项目是否允许“0 个仓库、仅文档”模式？推荐允许，但进入代码分析前必须补仓库。
