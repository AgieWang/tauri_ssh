## Context

Tauri SSH 是 Tauri 2.x 桌面应用，前端为 React/TypeScript，后端为 Rust，持久化使用 rusqlite，业务代码遵循 Command → Service → Database 三层架构。现有系统已经具备 AI Provider、加密凭据、Skill、经验库、Git 工作区、审计、MCP、后台操作和浏览器 Dev API，本 change 在这些能力上增加统一知识中枢；动机与范围见 [proposal.md](./proposal.md)。

知识事实来自三类边界不同的来源：

- Git：团队共享文档、历史源码、Commit、Tag 和版本证据。
- 禅道：需求、任务、Bug、测试和执行过程事实。
- 本地文件/源码：用户授权的本机补充证据，不天然具备团队共享和历史可信度。

首期必须在不部署服务器向量数据库的情况下运行，索引与元数据保存在每个客户端。远程依赖仅在用户选择远程 Embedding、聊天模型或禅道同步时使用。任何历史问答都必须保持项目和版本隔离，所有重要结论必须可追溯到原始来源。

## Goals / Non-Goals

**Goals:**

- 在现有 Tauri 三层架构内建立统一的项目、版本、来源、文档、片段、向量、关系和任务模型。
- 让 Git 文档、禅道事实、历史/本地源码、生成文档和经验使用相同检索及引用协议。
- 同时支持本地和远程 Embedding，并通过 Profile 指纹和蓝绿索引保证切换安全。
- 通过版本硬过滤、FTS5、向量和关系图融合实现可解释的混合检索。
- 先由确定性代码生成事实文档，再允许大模型生成有引用的解释与分析。
- 对本地路径、凭据、源码秘密、远程处理和 MCP 实施默认安全的统一治理。
- 通过增量同步、内容哈希、批处理和持久化任务状态支持大型知识源。

**Non-Goals:**

- 首期不建设集中式知识服务、服务器向量数据库或多人实时编辑。
- 不在知识同步时自动 checkout、stash、reset 或修改用户 Git 工作区。
- 不通过知识库反向修改禅道需求、任务、Bug 或测试结果。
- 不执行被分析仓库的构建、测试、脚本、Hook 或二进制。
- 不保证静态分析解析反射、运行时注入和所有动态调用。
- 不从不存在的历史资料生成可信事实，也不让未确认 AI 关系承担事实权重。
- 不在首期完成 OCR、复杂扫描 PDF 或所有编程语言的精确 AST 支持。

## Decisions

### 1. 采用客户端本地知识索引，Git/禅道保留来源事实

知识元数据、FTS、向量、同步游标和任务状态保存在 Tauri SSH 本地 SQLite。团队共享通过已有 Git 平台和禅道实现，不同步客户端 SQLite 文件。

理由：

- 与当前桌面架构和离线使用模式一致。
- 避免首期引入集中服务、租户权限和服务器运维。
- 源文档、Commit 和禅道实体仍可独立核查。

替代方案：

- 立即部署 PostgreSQL + 向量数据库：团队一致性更强，但显著扩大基础设施、安全和运维范围，留到 V0.4。
- Git 提交预计算向量：可共享结果，但模型、平台字节序、Profile 生命周期和仓库体积治理复杂，首期不采用。

### 2. 使用统一核心模型加来源扩展表

核心表负责：

- `knowledge_projects`
- `knowledge_releases`
- `knowledge_sources`
- `knowledge_documents`
- `knowledge_document_versions`
- `knowledge_chunks`
- `knowledge_embedding_profiles`
- `knowledge_chunk_embeddings`
- `knowledge_relations`
- `knowledge_jobs`

禅道和源码使用扩展表保存来源特有事实与同步状态，最终通过逻辑文档、片段和通用关系进入统一检索。

理由：

- 避免为每种来源复制一套全文、向量和引用链路。
- 保留禅道游标、外部 ID、代码符号和行号等专属结构。
- 新来源可以继续通过适配器和扩展表接入。

替代方案：

- 所有信息放入通用 JSON：迁移简单，但唯一约束、增量查询、关系遍历和数据质量难以保证。
- 每类来源完全独立索引：实现初期快，但检索、权限和 RAG 会出现多套逻辑。

### 3. 后端按 Command → Service → Database 分层并拆分领域模块

Command 只负责参数校验、启动后台任务、查询状态和错误转换；Service 负责同步、解析、分块、Embedding、关系、检索、RAG、文档生成及安全决策；Database 负责事务、DAO、FTS、向量 BLOB 和迁移。

领域模块：

- catalog/source sync
- parser/chunker
- embedding local/remote
- retrieval/RAG
- Zentao adapter/sync/generator
- source code snapshot/analyzer/relation resolver
- governance/audit

理由：知识库功能跨文件、网络、模型和数据库，若集中在 Command 或单一 Service 中将无法测试和恢复。

### 4. 使用适配器边界隔离来源和模型差异

定义稳定边界：

- `KnowledgeSourceAdapter`：发现、读取、增量游标和来源引用。
- `EmbeddingProvider`：健康检查、Profile、文档向量和查询向量。
- `ZentaoApiAdapter`：版本探测、分页实体和能力矩阵。
- `LanguageAnalyzer`：语言识别、符号和单文件关系提取。

业务层只依赖接口，不把固定禅道路径、模型协议或解析库散落在业务代码中。

理由：禅道版本、远程 Embedding 协议和语言解析器都存在现实差异，需要可替换适配器和契约测试。

### 5. Profile 指纹定义向量兼容性

Profile 指纹至少包含：

- local/remote 模式
- Provider 协议与端点身份
- Provider key
- 模型及修订
- 实际维度
- 归一化方式
- query/document prefix
- 分块策略版本
- 内容规范化版本

所有向量查询必须限定活动 Profile。维度相同不代表兼容。

理由：模型或分块变化会改变语义空间，混用会产生看似有效但错误的排序。

### 6. 使用蓝绿索引切换

保存影响指纹的设置时创建非活动 Profile；在独立索引中全量生成向量，完成完整性检查后通过事务原子激活。旧 Profile 保留一段时间用于回滚。

失败行为：

- 新索引标记失败。
- 旧索引继续服务。
- 不删除旧向量。
- 用户可从失败批次重试。

替代方案：

- 原地重建：磁盘占用小，但构建中检索不完整，失败后无可靠回滚。

### 7. FTS5、向量和关系并行召回，元数据先过滤

查询顺序：

1. 确定性解析项目、版本、需求编号、符号和文档类型。
2. 应用项目、版本、快照和权限硬过滤。
3. 并行执行 FTS5、活动 Profile 向量和有限深度关系扩展。
4. 通过 RRF 或归一化加权融合。
5. 生成上下文和稳定引用。

精确版本、需求编号、符号和已确认关系获得额外权重。AI Query Rewrite 只在确定性规则无法解析时使用，其输出必须映射到已存在实体。

理由：单纯向量检索不适合版本号、类名、字段和 Commit；单纯 FTS 无法覆盖同义表达；关系图用于连接需求、代码和测试。

### 8. 首期向量保存为 SQLite BLOB，达到阈值再增加 ANN

向量使用 `f32` 小端 BLOB 保存，同时记录维度和范数。查询先做硬过滤，再在 Rust 中计算候选余弦相似度。

评估本地 HNSW 的条件：

- 活动片段超过约 20 万。
- 跨项目向量查询 P95 超过 500ms。
- 候选向量加载明显影响前台内存或延迟。

SQLite 始终是事实来源，ANN 索引必须可重建。

理由：先避免平台构建和索引恢复复杂度，以真实规模决定 ANN。

### 9. 确定性文档先于 AI 摘要

禅道和源码分析先以固定模板生成项目概览、需求基线、追踪矩阵、测试报告、模块文档、API/数据库文档和调用链。事实指标由代码计算，每条记录携带实体 ID、Commit、快照或行号。

可选 AI 摘要：

- 只读取已生成事实片段。
- 与事实区域分开保存。
- 标记 Provider、模型和生成时间。
- 每项结论必须有可验证引用。
- 引用校验失败时删除或标记待核实。

理由：AI 擅长归纳，但不应决定需求状态、工时、测试结果、符号签名或 Commit 事实。

### 10. 禅道同步使用能力探测和独立实体游标

连接时探测 API 版本、认证和实体能力，选择 Endpoint Profile。产品、项目、执行、需求、任务、Bug、测试等实体分别维护游标；只有某实体类型的全部分页成功后才推进成功游标。

删除采用两阶段：

1. 本次全量不可见时增加 `missing_count`。
2. 连续满足确认条件后标记删除，保留历史快照。

项目、执行和发布必须显式映射到知识项目/版本，无法识别时进入 `unversioned`。

理由：不同禅道版本和权限下接口差异大；单一全局游标会放大失败和数据丢失风险。

### 11. 源码分析基于不可变快照和分层质量

快照类型：

- Git Commit/Tag：不可变历史事实。
- 分支头：记录解析时 Commit。
- 工作树：记录基线、dirty 状态和文件哈希。
- 非 Git 目录：记录采集时间和文件哈希。

历史内容通过 Git 对象读取，不 checkout。分析质量分为 `ast`、`structured_fallback`、`text_only`、`skipped`。符号键包含来源、路径、类型、限定名和签名哈希。

跨文件关系保存解析器、证据位置、置信度和确认状态；动态调用不能伪装成确定关系。

理由：必须同时支持精确语言分析和可用的降级路径，并避免工作树临时内容污染发布版本。

### 12. 后台任务使用持久化检查点和幂等批次

同步、分块、模型下载、向量化、禅道同步、源码解析和全量重建均运行在异步后台任务中。每个批次通过业务唯一键和内容哈希保证幂等，阶段、计数、心跳、错误和检查点写入 SQLite。

应用启动时将失去心跳的任务标记 `interrupted`，用户可重试。任务事件通过轮询 Command 和 Tauri Event 提供。

理由：长任务不能阻塞 IPC，且桌面应用可能随时关闭。

### 13. 安全治理在读取、落盘、远程和输出四个阶段执行

安全检查点：

1. 读取：来源根目录、canonical path、符号链接、URL 主机和凭据引用。
2. 落盘：敏感级别、原始快照策略、日志脱敏和内容哈希。
3. 远程：系统开关、来源开关、文档级别和秘密检测。
4. 输出：前端、RAG、MCP 和审计权限过滤。

代码来源默认禁止远程 Embedding。远程 Embedding 和远程聊天使用独立开关。本地模式失败不得自动回退远程。

前端不直接读取文件、调用禅道或访问数据库；Rust 后端不向前端返回密钥。

### 14. 浏览器 Dev API 与桌面 Command 保持同一 Service

为关键页面验收提供与 Tauri Command 等价的浏览器 Dev API，但两者必须调用同一 Service 和安全校验，不能形成仅开发环境可绕过的逻辑。

理由：项目要求前端页面通过 Codex 内置浏览器或 Chrome 验收，同时必须保持桌面实际行为一致。

## Risks / Trade-offs

- [本地模型和 ONNX Runtime 增加包体、构建与跨平台风险] → 模型按需下载/离线导入，正式依赖在 Windows、macOS、Linux Spike 后锁定。
- [SQLite 线性向量扫描在大规模下变慢] → 先硬过滤和性能基线；达到明确阈值后增加可重建本地 HNSW。
- [蓝绿索引暂时增加磁盘占用] → 提供重建估算、旧 Profile 保留期和安全清理。
- [中文 FTS5 分词效果受运行环境影响] → 运行时探测 trigram，回退 unicode61，并用向量检索补充。
- [禅道版本、认证和字段差异] → 能力探测、Endpoint Profile、脱敏真实 Fixture 契约测试。
- [需求与 Commit 缺少显式关系] → 约定 Commit trailer、手工确认、AI 只提供未确认建议。
- [静态源码分析无法覆盖动态调用] → 暴露分析级别和置信度，保留未知而不是制造确定关系。
- [本地未提交源码被误认为发布事实] → 工作树独立快照并强制展示 dirty 与基线 Commit。
- [内部文档或源码被远程发送] → 远程默认关闭，多层授权、秘密阻断、上下文预览和审计。
- [每个客户端重复远程向量化产生费用] → 内容哈希、批量请求、重试退避和字符量估算；集中索引留作后续演进。
- [知识表和任务数量使单一 SQLite 连接成为瓶颈] → WAL、短事务、后台批次、查询索引和基准测试；达到瓶颈后再评估连接池或拆库。
- [范围过大导致一次性交付风险] → 按迁移阶段交付，每阶段形成可运行闭环并保持旧经验库接口兼容。

## Migration Plan

1. **技术 Spike**
   - 验证本地 Embedding、FTS tokenizer、向量规模、目标禅道 API 和 P0 语言解析器。
   - 产出兼容矩阵和依赖锁定结果，不修改现有数据。
2. **核心目录与文档检索**
   - 从当前 schema 版本开始追加迁移，创建项目、版本、来源、文档、片段、关系和任务表。
   - 接入 Git/本地文档同步、解析、FTS、文档页和基础搜索。
3. **Embedding 和蓝绿索引**
   - 增加 Profile 与向量表，先交付本地模式。
   - 通过真实评测后增加远程模式、授权矩阵、重建估算和回滚。
4. **混合 RAG**
   - 交付项目/版本过滤、融合排序、引用、上下文预览和知识问答。
   - 旧经验库接口保持兼容，逐步迁移到统一召回。
5. **禅道闭环**
   - 先接一个真实禅道项目和一个发布版本。
   - 完成需求、任务、测试同步及追踪矩阵，再扩展 Bug、评论、构建和发布。
6. **源码知识闭环**
   - 先分析一个发布 Tag 和工作树，支持 P0 语言、符号、关键调用链和本地向量。
   - 验证版本引用后再开放非 Git 目录和更多语言。
7. **治理与 MCP**
   - 在每阶段同步接入审计和远程授权；最后开放只读 MCP 和受控关系/经验写入。
8. **回滚**
   - 数据库迁移不删除旧表和旧字段。
   - 新功能通过模块入口和设置开关禁用。
   - Profile 失败或回滚时保留上一活动索引。
   - 禅道和代码源可禁用并保留历史索引；必要时按来源删除新增索引，不影响原经验库。

## Open Questions

- 目标生产禅道实例的具体版本、认证模式和测试相关接口能力，需要在实现适配器前通过只读 Spike 确认。
- 本地默认模型最终选择 `multilingual-e5-small` 还是 `bge-small-zh-v1.5`，由中文需求、代码标识符和跨项目评测决定。
- P0 语言是否统一采用 Tree-sitter 生态或对 Java/Vue/SQL 使用专用解析器，由准确率、包体和三平台构建 Spike 决定。
- 本地向量由线性扫描升级到 HNSW 的实际片段阈值，以目标机器性能基准为准。
