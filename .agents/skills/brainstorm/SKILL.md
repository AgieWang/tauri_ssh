# 方案发散与收敛

## 能力边界

本 Skill 只负责“先探索再收敛”，不负责模块边界设计、正式决策记录或代码实现。

- 模块职责、依赖方向和跨进程边界交给 `architecture-design`。
- 需要形成正式、可追踪的技术取舍时交给 `tech-decision`。
- 用户已明确要求实施时，不因出现“方案”“怎么做”而自动加载本 Skill。
- 单一明确问题、代码定位、Bug 诊断或普通建议不需要本 Skill。

## 探索原则

1. 先基于真实仓库、运行环境和用户目标建立约束，避免脱离现状自由联想。
2. 同时保留不同机制的候选项，而不是用同一方案换名字凑数量。
3. 明确区分事实、假设、未知项和建议。
4. 准确性、安全、数据完整性和可验证性是硬约束，不能作为节省成本的交换项。
5. 优先提出可逆、可渐进验证的路径；外部写入和破坏性动作不因讨论而获得授权。

## 工作流程

### 1. 定义问题空间

- 目标：用户最终要改善什么结果。
- 范围：涉及哪些模块、用户、平台或数据。
- 约束：兼容性、性能、安全、时间、依赖和维护成本。
- 成功标准：哪些证据能够证明方案有效。
- 未知项：哪些信息需要读取源码、配置、数据库或运行时才能确认。

### 2. 生成候选方向

通常提出 2～4 个实质不同的候选方向；若只有一个合理方向，应直接说明，不强行发散。每个候选至少写清：

- 核心机制与适用条件。
- 需要改变和保持不变的内容。
- 主要收益、代价和失败模式。
- 最小验证实验或淘汰条件。

### 3. 比较与收敛

使用任务相关维度比较，不机械套固定权重。常用维度包括：

- 正确性与契约完整性。
- 与现有架构的一致性。
- 实现和迁移复杂度。
- 运行性能与资源消耗。
- 安全、数据和运维风险。
- 测试、回滚与长期维护成本。

推荐可以是单一方案，也可以是有明确边界的混合方案。必须解释为何适合当前上下文，并列出使结论改变的条件。

## 输出要求

输出应包含：

1. 问题重述与已知约束。
2. 关键假设和待确认事实。
3. 候选方案及真实差异。
4. 对比维度、风险和验证办法。
5. 推荐方向及不推荐其他方向的具体原因。
6. 下一步取证或决策动作；未经授权不直接实施。

## 不应触发示例

- “按既定方案实现该功能。”
- “定位这个 invoke 报错，先不要修改。”
- “拆分 Command、Service、Database 的职责。”
- “把方案 A 与 B 的最终决策写成 ADR。”
- “告诉我这个函数在哪个文件。”

## 按需参考

需要完整的候选方案模板、对比矩阵或收敛检查表时，读取 [references/option-evaluation.md](references/option-evaluation.md)。不要默认加载通用技术栈和包推荐清单。

## 完成条件

- 候选方案具有机制上的真实差异。
- 约束、假设、未知项和证据需求已显式区分。
- 推荐没有牺牲准确性、安全或必要验证。
- 输出停留在用户授权范围内；若用户只要求讨论，没有修改代码或外部状态。
- 若进入模块设计或正式决策阶段，已明确交接到相邻 Skill。
