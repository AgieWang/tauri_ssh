# /next

这是只读的项目路线分析工作流。普通句子中的“下一步”“建议”“优先级”不触发全仓扫描。

## 收集证据

并行收集与建议直接相关的最小证据：

- 最近 10 条非合并提交和当前未提交变更。
- `docs/tasks/active/`、项目状态文档、TODO/FIXME 中有当前证据支持的未完成项。
- Rust Commands → Services → Database 分层、前端 pages → API → store 调用链中的明显缺口。
- 当前测试/构建失败证据；没有运行过就明确标注“未验证”，不得猜测。

不要为了“项目全貌”读取所有源码。先用 `rg --files`、`rg` 和提交路径定位热点，再按需打开具体文件。

## 排序规则

1. 用户已明确的未完成任务和阻塞项。
2. 会导致当前功能不正确的契约、权限、数据库或运行时缺口。
3. 已有实现链路中的缺层、失败测试和高置信 TODO/FIXME。
4. 最近开发方向的自然延续。
5. 只有前四类均无可靠候选时，才提出新功能方向。

## 输出

- 当前状态：仅列与决策有关的已验证事实。
- 推荐下一步：只给一个，包含来源、原因、目标文件、完成标准和验证方式。
- 备选方向：最多三个，并说明为什么优先级更低。
- 风险/未知：列出需要真实数据库、服务、浏览器或用户决策才能确认的事项。

## 强制规则

- 全程只读，不修改代码、文档、任务状态或 Git。
- 不预估工期，不把提交数量当作完成度，不把 build 通过当作生产验收。
- 所有建议必须落到现有文件、任务或可验证缺口；不得凭通用模板发明需求。
- 数据库、远端和真实页面结论必须标注当前是否已验证。

## 不应触发

- “修完后告诉我下一步怎么验证”——直接回答当前任务的验证步骤。
- “把状态字段改成 enabled”——业务字段修改，不是项目路线分析。
- “这个 API 方案你建议哪个”——使用 `brainstorm` 或 `tech-decision`。
