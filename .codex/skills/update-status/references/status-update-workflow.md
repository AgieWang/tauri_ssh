# 项目状态增量更新参考

仅在显式 `/update-status` 时读取。

## 证据源

```bash
git status -s
git log -20 --format='%H|%an|%cn|%s' --no-merges
rg --files docs/tasks/active docs/architecture
rg -n 'TODO|FIXME|todo!\(|unimplemented!\(' src-tauri/src src
```

按需读取目标文档和变更涉及的 Commands/Services/Database/Models、Pages/API/Store。目录不存在时标记“不适用”，不要当成零项。

## 提交过滤

- merge、cherry-pick、`sync:`、`upstream:`、纯 `docs:`/`chore:` 可以从“业务活动”统计中单列，但不能删除其对文档的真实影响。
- Author 与 Committer 不同只是线索，不足以断言 cherry-pick。
- `feat:`/`fix:` 也不代表已验收，仍需任务和验证证据。

## 候选表

| 任务/需求标识 | 当前状态 | 建议状态 | 证据 | 置信度 | 目标文件 | 修改理由 |
| ------------- | -------- | -------- | ---- | ------ | -------- | -------- |

匹配顺序：稳定 ID → 精确标题 → 文件/模块与功能组合。只有模糊关键词时列为待确认，不自动写。

## 联动规则

- 项目状态、待办、需求引用同一任务时使用稳定标识关联。
- 标记完成前至少需要实现证据和对应验证；生产验收必须有真实环境证据。
- 新 TODO 记录文件和行号；移动/删除后先追踪变更，不凭位置变化判定完成。
- 活跃任务进度使用明确的 `[x]/总项`；跳过不属于分母的说明项。
- 依赖版本变化从当前 `Cargo.toml`/`package.json` 读取，不从旧文档复制。

## 报告模板

```markdown
# 项目状态更新报告

## 结论

- 已更新：...
- 未更新：...
- 待确认：...

## 文件变更

| 文档 | 内容 | 为什么修改 | 证据 |
| ---- | ---- | ---------- | ---- |

## 验证层级

| 工作项 | 已实现 | 测试/构建 | 真实环境 | 状态文档写法 |
| ------ | ------ | --------- | -------- | ------------ |

## 回滚

- 本轮 patch/备份位置或恢复说明：...
```

## 验证

- 所有状态变化有可点击/可定位来源。
- 统计重新计算且分母明确。
- 没有覆盖人工说明或其他会话改动。
- 时间为 `Asia/Shanghai`，Markdown/UTF-8/链接和 `git diff --check` 通过。
