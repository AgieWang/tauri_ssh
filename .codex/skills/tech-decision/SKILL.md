# 技术决策记录

## 能力边界

本 Skill 用于“作出并记录取舍”，前提是候选和约束已经足够明确。

- 尚在发散可能性时使用 `brainstorm`。
- 需要设计模块职责和依赖方向时使用 `architecture-design`。
- 已有明确决策、只需要实现时，不加载本 Skill。
- 普通偏好、局部编码选择或无需长期追踪的小调整不必创建 ADR。

## 何时值得记录

符合下列任一条件时通常需要正式记录：

- 影响多个模块、进程边界、数据模型或公共契约。
- 引入长期依赖、迁移成本或难以逆转的基础设施。
- 在安全、性能、兼容性、交付速度之间存在实质权衡。
- 团队未来可能重新质疑，需要保留当时证据和适用条件。
- 替换、废弃或修订已有决策。

## 决策流程

### 1. 固化上下文

- 描述问题、影响范围、当前状态和变化压力。
- 列出硬约束、成功标准和不在范围内的事项。
- 引用真实源码、配置、数据库、日志或运行时证据；区分事实与假设。

### 2. 保留可行候选

- 仅比较满足硬约束的方案。
- 每个方案说明核心机制、影响文件、迁移方式和失败模式。
- 不把“保持现状”遗漏掉；它通常是有效基线。
- 不用方案数量替代分析质量。

### 3. 做出取舍

依据当前任务选择维度，至少考虑：

- 正确性、契约和数据完整性。
- 架构一致性与长期维护成本。
- 安全、权限和外部依赖风险。
- 性能、资源和执行效率。
- 迁移、测试、可观测性与回滚能力。

明确写出：采纳什么、拒绝什么、为什么现在做，以及哪些条件会使决策失效。

### 4. 定义后果

- 正向收益和可接受代价。
- 新增风险、技术债与监控项。
- 实施顺序、验证门禁与回滚条件。
- 需要后续完成的任务，但不能把 ADR 当作实施授权。

## 状态规范

建议使用：`Proposed`、`Accepted`、`Superseded`、`Deprecated`、`Rejected`。

- 未获得相应授权或评审时，不擅自标为 `Accepted`。
- 修订旧决策时保留原记录并建立替代关系。
- 证据变化时更新状态和复审日期，不悄悄改写历史理由。

## 输出要求

决策输出至少包含：

1. 标题、日期、状态和决策所有者。
2. 背景、问题、范围和约束。
3. 已验证证据与未验证假设。
4. 候选方案及对比。
5. 最终决策和明确理由。
6. 正负影响、风险与缓解措施。
7. 实施、验证、回滚和复审条件。

## 不应触发示例

- “先想想还有哪些实现方式。”
- “这个模块应该放 Command 还是 Service？”
- “按已经批准的设计开始编码。”
- “修复一个局部 TypeScript 类型错误。”

## 按需参考

需要完整 ADR 模板和评审清单时，读取 [references/adr-template.md](references/adr-template.md)。项目内文档只有用户明确要求时才创建，并遵守 `docs/` 存放规则。

## 完成条件

- 结论由当前证据和明确约束支持。
- 被拒方案及拒绝原因可复审。
- 决策状态与用户/团队授权一致。
- 影响、验证、回滚和失效条件均可执行。
- 没有把正式决策记录误当成代码实施或外部操作授权。
